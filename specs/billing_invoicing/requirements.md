## 2. Local requirements

### 2.1 Reused from #7 and #8

Texts are #8's, verbatim except where a *#9 note* is attached; line-unwrapped only. Where #8's text named a C#- or MS-SQL-specific mechanism, the clause is rewritten stack-neutrally and the note says so.

**BI1.** THE SYSTEM SHALL issue an invoice **only** in response to a `billing.invoice.issue` NATS RPC request, and the Billing service SHALL register **no** Kafka consumer, **no** fact-stream task and **no** idempotent-consumer runner of any kind — `saga.md` §5 gives Billing no consumed facts, and the orchestrator is the only component permitted to translate `order.despatched.v1` into the issue command (`saga.md` §3.1 step 4). IF a fact-stream consumer is introduced into the Billing service, THEN the structural guard of `BI1` SHALL fail.

> *#9 note.* #8's text named a `BackgroundService` and its guard enumerated the built host's `IHostedService`s. The #9 guard is two existing instruments: `tests/architecture/test_kafka_client_confinement.py` (the literal importer set holds Billing's **publisher** only; an `AIOKafkaConsumer` import anywhere in `otc_billing` fails it) and `services/billing/tests/integration/test_billing_host_lifespan.py::test_the_lifespan_starts_the_responder_and_the_relay_and_awaits_both_on_shutdown` (the runtime's task set is exactly `{"nats-responder", "outbox-relay"}`). Both already exist from feature 19; this feature arms them, it does not write them. No idempotent-consumer parity case goes live (`design.md` §10.3).

**BI2.** WHEN a `billing.invoice.issue` request arrives whose `x-correlation-id` or `x-request-id` header is absent or is not a well-formed `UniqueId`, or whose payload fails schema validation — an empty `lines` list, a non-positive `units`, a negative `unitPrice`, a malformed `orderReference`, a currency that is not `^[A-Z]{3}$`, a negative `discount`, **or a `discount` that exceeds `Σ(unitPrice × units)`** — THE SYSTEM SHALL answer `VALIDATION_FAILED` **before dispatching the command**, SHALL create no invoice, SHALL append no ledger entry and SHALL emit no fact.

> *#9 note.* The schema half (`lines` non-empty, `units ≥ 1`, the patterns, strict integers) is the generated `InvoiceIssueRequestPayload` through `from_wire_json`; the generated `MinorUnits` admits a negative value, so `unitPrice ≥ 0`, `discount ≥ 0` and `discount ≤ Σ(unitPrice × units)` are edge checks in `presentation/invoice_wire.py` (#7 `presentation/dto/invoice.dto.ts:39-41, 112-115`; #8 `InvoiceRequestValidator.cs:61, 68-80`). **The placement clause is proven by observing the entry, never the residue** (#7's review `N2` / `N10`, inherited through #8): a unit case asserts the dispatcher was called **zero** times; the integration case asserts the outcome and says in its own comment that it does not prove placement.

**BI3.** IF a `billing.invoice.issue` request names a `(retailerCode, companyCode)` pair for which no credit line exists, THEN THE SYSTEM SHALL answer `NOT_FOUND` naming the pair, SHALL create no invoice, SHALL append no ledger entry and SHALL emit no fact.

**BI4.** IF a `billing.invoice.issue` request names a `currency` other than the credit line's, THEN THE SYSTEM SHALL answer `VALIDATION_FAILED` carrying the expected and the received currency, SHALL create no invoice, SHALL append no ledger entry and SHALL emit no fact (a consequence of **M2** and of **B3**).

**BI5.** IF a `billing.invoice.issue` request names an order that holds **no active credit hold** on the named credit line — because the hold was refused, because a cancellation already released it, or because no hold was ever placed — THEN THE SYSTEM SHALL answer `PRECONDITION_FAILED` carrying the stable code of `NoActiveHoldError`, SHALL create no invoice, SHALL append no ledger entry, SHALL emit no fact, and SHALL leave the order's existing ledger rows exactly as they were.

> *#9 note.* "Active hold" is `BC12`'s structural reading (a `hold` entry and neither a `consume` nor a `release` entry), gate ruling G1 of feature 19 (`progress/spec_billing_credit.md` § Gate ruling): a **zero-amount** hold is active and is consumed (`BI35`), where #7 (`invoice-issue.handler.ts:106`, `activeHold <= 0`) and #8 (`InvoiceIssueService.cs`, `ActiveHoldOf(...) <= 0`) would refuse it. The refusal is raised by `BuyerCredit.consume` itself (`domain/buyer_credit.py:386-399`), called **before** the invoice number is allocated (`design.md` §6.2), so the counter row is never touched on this path. The final clause is #7's review finding `N3` (written, never asserted there): asserted here from the start by re-reading the order's ledger rows after the refusal.

**BI6.** THE SYSTEM SHALL emit **no fact other than `invoice.issued.v1`** in response to a `billing.invoice.issue` request, on any path it can reach. There is no invoice-rejection fact in the catalogue of `domain-model.md` §7.2, so every non-success outcome of this subject is an `RpcError` reply and every success is either a new invoice carrying exactly one fact or an idempotent repeat carrying none.

**BI7.** WHEN an invoice is issued for an order holding an active credit hold, THE SYSTEM SHALL, **in one database transaction**, insert the invoice row and its line rows, append exactly one `consume` ledger entry of that order's active hold to the `BuyerCredit` aggregate, and record exactly one `outbox` row, whose `event_type` is `invoice.issued.v1`; and IF any of those writes fails, THEN THE SYSTEM SHALL roll back all of them, leaving no invoice row, no invoice line, no ledger entry and no outbox row, and SHALL answer with an error reply.

> *#9 note.* The deviation from `domain-model.md` §8 rule 6 is re-derived against #9's code in `design.md` §6.5. Unlike #8 (ambient `DbContext`), #9 has an explicit transaction object, as #7 had: `CreditTransactions.run(work)` hands `work` one `CreditTransaction` whose `credits`, `invoices` and `invoice_numbers` are all bound to **one** `AsyncSession` (feature 19's seam, `specs/billing_credit/design.md` §6.4, §15.2).

**BI8.** THE SYSTEM SHALL acquire row locks in the Billing write model in exactly one order — the `credits` row (and its ledger reads), then any `invoices` row, then the `invoice_number_sequences` row — in every transaction of the service, present and future; and two concurrent `billing.invoice.issue` requests for the same order SHALL produce exactly one invoice, exactly one `consume` entry and exactly one `invoice.issued.v1`, with no deadlock and no lock-wait timeout.

> *#9 note.* In #9 the issue path takes **two** row locks — the `credits` row `FOR UPDATE` and the counter row `FOR UPDATE` — and re-reads `invoices` **without** a lock between them: after the credits lock is granted, the re-read is a new statement under the pinned `READ COMMITTED`, so it sees what a competitor committed (feature 19's `L12`, Fulfillment's F8 in-lock re-read, `services/fulfillment/src/otc_fulfillment/application/despatch_creation.py`). #8 recorded that its `UPDLOCK` on the same read was not load-bearing (#8 `design.md` §16 `L8`); #7 locked it `FOR UPDATE` (`invoice.repository.ts:56`). The ordering clause is guarded by an ordered call log of the three calls (lock, re-read, allocate) — #7's review `N4` found a two-element log — and the race cannot see an ordering inversion (#7's `N5`), which the race file's header says.
>
> **Binding on feature 22:** `billing.payment.register` resolves its invoice by `invoiceId` / `invoiceReference` with an **unlocked** read to learn the `(retailerCode, companyCode)` pair, then locks the `credits` row, then re-reads the invoice and verifies its status before updating it. Updating the invoice row first would put an `invoices` lock before a `credits` lock.

**BI9.** WHILE an invoice already exists for the `orderReference` named by a `billing.invoice.issue` request, THE SYSTEM SHALL answer with the existing `invoiceId`, `invoiceReference`, `invoiceDate`, `currency`, `totalAmount` and current `status`, with `created: false`, SHALL write nothing at all — no second invoice, no second `consume` entry, no row of any kind — and SHALL emit no second fact (invariant **B7**, `saga.md` §6 layer 3). This holds whether the existing invoice is `issued` or already `paid`.

> *#9 note.* #8's text names `invoiceId` but #8's reply never carried it (`InvoiceIssueService.cs` `BuildReply` passes no id; the record defaults it to `null`, omitted). #7 sends it (`invoice-issue.handler.ts:19-41`). #9 sends it on every reply, `created` true or false — the text both predecessors wrote, and #7's bytes (`design.md` §16.2).

**BI10.** THE SYSTEM SHALL make an invoice whose status is `paid` without a `paidAt`, or whose status is `issued` with a `paidAt`, **unrepresentable in the domain layer**: the two are one value, not two independent fields, and no member of the aggregate assigns either of them separately; and IF a stored row is read whose `status` and `paid_at` disagree, THEN THE SYSTEM SHALL raise a domain error naming the invoice rather than construct the aggregate or its snapshot (invariant **B9**).

**BI11.** THE SYSTEM SHALL derive an invoice's `amount` as `Σ(unitPrice × units)` over its lines and its `totalAmount` as `amount − discount`, SHALL refuse construction when the line list is empty, when a line's currency differs from the invoice's, or when `totalAmount` would be negative, and SHALL expose no setter for any of `amount`, `discount` or `totalAmount` (invariant **B6**).

**BI12.** THE SYSTEM SHALL allocate each `invoiceReference` as `INV-` plus a zero-padded six-digit sequence, unique across the service and never reassigned, using the same single-row counter-table mechanism `ORD-` and `DES-` use; two concurrent allocations SHALL never yield the same value; and the first live allocation SHALL continue past the highest reference already present in `invoices` rather than colliding with it.

> *#9 note.* The counter SQL already exists and is already guarded (`services/billing/src/otc_billing/infrastructure/persistence/sequences.py`, backlog 211; `services/billing/tests/integration/test_billing_counter_seed.py`, five cases). This feature adds the allocator class that executes it in the caller's transaction (a copy of `despatch_number_allocator.py`'s shape) and ports Fulfillment's six allocator tests through the real transactions object. The seed writes `INV-000001` … `INV-000005` (`services/seed/src/otc_seed/domain/data/sagas.py:19`).

**BI13.** THE SYSTEM SHALL stamp `invoice.issued.v1` with `aggregateId` = the invoice's own id, `correlationId` = the order id taken from `x-correlation-id`, `causationId` = the request id taken from `x-request-id`, and `occurredAt` = the invoice's `invoiceDate` read once from the clock port — one event type, one builder, one call site; and the test that proves it SHALL prove **provenance**, by driving the id source and the clock through injected values and asserting the stamped values are those values, never merely that they are non-default and distinct.

**BI14.** WHERE feature 22 is not yet implemented, THE SYSTEM SHALL nevertheless provide `Invoice.mark_paid`, which moves an `issued` invoice to `paid`, sets `paidAt` in the same indivisible assignment, and appends exactly one `payment.received.v1` carrying the payment's own reference, amount, currency, value date and source; and IF `mark_paid` is called on an invoice already `paid`, or with an amount or currency other than the invoice's `totalAmount` and currency, THEN THE SYSTEM SHALL raise a domain error, change nothing and append no event (invariants **B8**, **B9**, **B10**; shared `R46`, and the amount clause of `R49`).

> *#9 note.* Two additions, both from #8's own record. (1) #8's round-1 review `D1`: corrupting the raised fact's `valueDate` and `source` left the whole suite green, because the test asserted only count, type and one field. In #9 **every** payload field of the raised `PaymentReceived` and its four identity fields are asserted against test-supplied, pairwise-distinct values, and each is corrupted in turn (`tasks.md` B9). (2) #8 id 57 (assigned to feature 22 by feature 19, `specs/billing_credit/design.md` §17.1): `mark_paid` **returns** the `PaymentReceived` it raised, so 22 can make `credit.released.v1`'s `causationId` its `eventId` — #7's amendment A1 shape (`invoice.ts:273, 311`). 22 calls it; 21 only ships the seam.

**BI15.** WHEN a `billing.invoice.list` request is received, THE SYSTEM SHALL answer with a page of invoice views filtered by any supplied `status`, `retailerCode`, `companyCode` and `orderReference`, SHALL return only invoices whose `invoiceDate` is at least `issuedBeforeMinutes` minutes before the current time when that filter is supplied, SHALL take the current time from the clock port as a parameter rather than reading an ambient system clock inside the query adapter, SHALL take no lock and open no write, and SHALL never mutate anything.

> *#9 note.* Ordered `invoice_date DESC, invoice_reference DESC`, the cutoff inclusive (`<=`) — #7 `invoice-read.repository.ts:37-48`, #8 `EfCoreInvoiceReadRepository.cs:43-55`, identical. Filters are exact, case-sensitive equality (feature 17's G2 ruling, feature 19's `BC28` note).

**BI16.** THE SYSTEM SHALL answer both new subjects with **bare JSON** — a plain reply object on success and a plain `RpcError` object on failure, with no framework packet envelope — through the one shared serializer; and the subject constants SHALL equal the `address` of their AsyncAPI channels character for character, read from `specs/shared/asyncapi.yaml` rather than retyped.

**BI21.** THE SYSTEM SHALL prove, in a test driven from **one** `Order` instance, that an invoice's `totalAmount` equals the order total for which the credit hold was placed: `Σ(unitPrice × units) − discount` over the `invoice.issue` request equals the `credit.hold` request's `amount.amount` and equals the order's own `total_amount`.

> *#9 note.* **Already realised by feature 16, guarded here without an Orders change.** `services/orders/src/otc_orders/application/saga/command_payloads.py` builds `discount=order.initial_discount.amount`, and `services/orders/tests/unit/saga/test_command_payloads.py` drives both payloads from one fixture order whose `(initial_amount, initial_discount, total_amount)` is asserted to be `(8465, 350, 8115)`: `test_credit_hold_amount_is_the_total_not_the_initial_amount_or_the_discount` asserts the hold amount `8115`, and `test_invoice_issue_lines_carry_units_and_unit_price_and_the_initial_discount` asserts the lines `3 × 1999 + 2 × 1234 = 8465` and the discount `350`. Unlike #8 (`Discount: 0` from hand-written literals, #8 `requirements.md` `BI21` note), #9's guard bites today; this feature **arms** it (substitute `0` for the discount, and `order.initial_amount` for the hold amount) and edits no file under `services/orders/`.

**BI22.** WHEN the Billing service first starts with the `billing.invoice.issue` responder registered, THE SYSTEM SHALL cause every `invoice.issue` row parked in `otc_orders.saga_commands` to be re-dispatched by the existing sweeper, one invoice to be issued per order, one `consume` entry to be appended per order, one `invoice.issued.v1` to be published per order, each of those orders to reach status `invoiced`, and each credit line's `availableCredit` to be **numerically unchanged** by the whole exercise — **and SHALL then stop there**, because `saga.md` §3.1 step 5 has the saga wait for the outside world: no internal timer, no polling, and no further command until a remittance arrives with feature 22.

> *#9 note.* The developer stack holds one such row: `ORD-000008`, `despatched`, `invoice.issue` `parked` (`progress/impl_billing_credit.md` §8, K5's register of altered live fixtures, lines 535 – 544). `ORD-000007` stops at `confirmed` and issues no `invoice.issue` (that register); `ORD-000009` is `cancelled`; `ORD-000090` exists only as a Billing ledger fixture. A fresh control order with a **non-zero discount** completes the live record (`design.md` §14).

**BI23.** THE SYSTEM SHALL render the invoice's `(status, paidAt)` pair as a **closed set of exactly two cases**, `issued` and `paid`, the `paid` case unconstructible without its instant, with no third case and no partially initialised case constructible, and the aggregate SHALL hold exactly one attribute of that type.

> *#9 note.* #7 had it from a TypeScript structural union (`domain/invoice.ts:56-57`); #8 constructed it as a closed abstract record hierarchy whose base constructor is `private protected` (`InvoiceState.cs:56`), because a struct always has a `default`. Python has neither sealed classes nor a zero value; the property is constructed from three parts (`design.md` §5.2): a `type InvoiceState = Issued | Paid` alias over two frozen, slotted dataclasses whose `__init_subclass__` raises `TypeError` (armed by B2d; the maintainer is told, and the decorator census is not extended, review §4.7) (closure for the type checker: every `match` ends in `assert_never`, so a third case is a `mypy --strict` error at every site); `Paid.__post_init__` refusing anything but an aware `datetime` (a `None` past the type checker — the Python counterpart of #8's `default(T)` — is a runtime error, not a state); and a structural test that the alias's members are exactly the two classes.

**BI24.** THE SYSTEM SHALL round-trip `paid_at` through the store such that an instant written as UTC is read back as the identical instant regardless of the host's and the database session's time zone, and SHALL distinguish a `NULL` `paid_at` from an instant — the nullable case included in the guard, not only the non-null one.

> *#9 note.* `timestamptz(3)` plus asyncpg's binary decode returns an aware UTC `datetime` or `None` (measured for this spec under session `TimeZone = 'Europe/Madrid'`: `datetime(…, tzinfo=timezone.utc)` with `utcoffset() == 0:00:00`, and `None` for the null row). The guard reads **through the production mapper** (#8 feature 19's review `D1`: a guard that re-implements the conversion proves nothing), under a non-UTC session `TimeZone`, `BC24`'s shape.

**BI25.** IF an invoice's `Σ(unitPrice × units)` or `amount − discount` would exceed the representable range of the money type, THEN THE SYSTEM SHALL raise a **domain error carrying a stable code**, never an unhandled runtime exception, and the responder SHALL map it to a code the saga dispatcher classifies as **terminal**.

> *#9 note.* Python `int` never wraps, so "not wrapped" is free; the stable code is not: an out-of-range `Σ` would otherwise reach `Money` (`money.invalid_amount`, `packages/shared_kernel/src/otc_shared_kernel/money.py:44-45`) or the `bigint` column. `Invoice.issue` checks its accumulated totals against int64 and raises `InvoiceTotalOverflowError` (`invoice.total_overflow`), mapped `DOMAIN_ERROR` (terminal) — feature 19's `BC30` shape. #8's "validator half" (an unchecked sum that wraps) has no Python counterpart; its #9 equivalent is `BI33`'s edge refusal of a `Σ` above int64, so a permanently-unrepresentable payload is refused before dispatch rather than inside the transaction.

**BI26.** THE SYSTEM SHALL classify `PRECONDITION_FAILED` as a **terminal** saga rejection, so that a `BI5` refusal stops the `invoice.issue` command row immediately with the reason recorded, rather than being retried to exhaustion; and a test SHALL read that classification from the dispatcher's own closed set rather than restating it.

> *#9 note.* The set is `TERMINAL_RPC_ERROR_CODES` (`services/orders/src/otc_orders/infrastructure/messaging/nats_saga_commands.py:65-75`, nine codes); a terminal `RpcError` resolves the row as rejected (feature 16's follow-up, commit `94ebf06`). The test is `tests/architecture/test_billing_rpc_error_retryability.py`, which already imports that set (feature 19's `BC27`).

**BI27.** THE SYSTEM SHALL treat the invoice `status` token as a closed set (`issued`, `paid`) parsed **loudly** — an unrecognised token raises rather than being coerced or skipped — and SHALL write only the lower-case contract tokens, so that the store's comparison and the domain's can never disagree about which invoices a filter selects.

> *#9 note.* PostgreSQL's deterministic collation compares exactly (measured for this spec: `'paid' = 'Paid'` is `false`), so the disagreement #8 closed against MS-SQL's case-insensitive collation cannot arise in the store; the loud parse is still owed, because a hand-written `'Paid'` row must not silently become an `issued` invoice or vanish from a `status = paid` filter without a sound. The `status` filter on the wire is the generated `InvoiceStatus` enum, which refuses anything but the two tokens.

**BI29.** THE SYSTEM SHALL seed the `invoice_number_sequences` counter row **atomically** — one statement whose insert and whose existence test are the same statement — never as a check-then-act pair; and the seed value SHALL continue past the highest `INV-` reference already present in `invoices`.

> *#9 note.* Realised by backlog 211's `SEED_INVOICE_SEQUENCE` (`INSERT … SELECT … WHERE NOT EXISTS … ON CONFLICT (id) DO NOTHING`, numeric `MAX`) and guarded by `test_billing_counter_seed.py` (sixteen concurrent first callers; a check-then-insert sentinel that must lose; the next number over a seeded database; a seven-digit reference; the `MAX` scan never run once the row exists). This feature **re-runs and cites** those five; the allocator class executes the constants, it does not restate them.

**BI31.** THE SYSTEM SHALL answer all five `billing.*` RPC subjects that exist after this feature (`billing.credit.hold`, `.release`, `.list`, `billing.invoice.issue`, `.list`) from **one** responder task, so that the service's request-concurrency bound, its one-scope-per-request rule and its shutdown drain exist in exactly one implementation guarded by exactly one set of tests.

### 2.2 New in #9

**BI32.** WHEN a `billing.invoice.list` reply carries an `issued` invoice, THE SYSTEM SHALL write its `paidAt` key with the value `null`, and WHEN it carries a `paid` invoice, THE SYSTEM SHALL write `paidAt` as the instant the invoice was paid; no other `null` SHALL appear in an invoice reply.

> *New in #9.* `asyncapi.yaml`'s `InvoiceView.paidAt` is `oneOf [Instant, null]` and not `required`, so both shapes validate. #7 writes `null` (`invoice-read.repository.ts:66`); #8 omits the key under its ratified nulls-omitted rule (#8 `BI28`, its gate record row 4). #9's wire rule, ratified in feature 8 (`packages/contracts/src/otc_contracts/wire.py` docstring: *"a `None` is written as an explicit `null` only for a field that the spec declares nullable"*; `generated/nullable.py`: `"asyncapi.InvoiceView": frozenset({"paidAt"})`), lands on #7's bytes. Applying a ratified rule is not a new decision (#8's gate record, row 4). Consumers (Gateway, feature 25; the n8n bank robot, feature 33) receive `null` for "not paid", as from #7.

**BI33.** IF a `billing.invoice.issue` request carries an `orderReference` longer than 20 characters, a line `units` above 2 147 483 647, or lines whose `Σ(unitPrice × units)` exceeds 9 223 372 036 854 775 807, THEN THE SYSTEM SHALL answer `VALIDATION_FAILED` before dispatching the command, writing nothing and emitting nothing.

> *New in #9.* Three values the generated schema admits and a column cannot hold: `orderReference` has a pattern but no maximum and `invoices.order_reference` is `varchar(20)` (feature 19's `BC33`, Fulfillment's FS28); `Quantity` has no maximum and `invoice_items.units` is `integer`, whose ORM range guard would refuse it only **inside** the transaction, after the counter row was locked — exactly #7's `N2` placement defect, one column over; `invoices.amount` is `bigint`. #7's JavaScript numbers and #8's `long` / `int` types each refused or wrapped these silently in their own way; Python's unbounded `int` reaches the column unless the edge stops it.

**BI34.** THE SYSTEM SHALL take the invoice's id, every invoice line's id, the `consume` entry's id and the `eventId` of every invoice fact from the id source the application supplies, at every site, and a test SHALL prove each site's value is the supplied one.

> *New in #9.* Feature 19's `BC36` (#8 id 49's lesson, recurred in #9 feature 17), extended to this aggregate. #7 minted ids inside the domain (`domain/invoice.ts:102`, `UniqueId.generate()`); #8 passed `newId` for lines and events but minted the invoice id in the service (`InvoiceIssueService.cs`, `UniqueId.New()`).

**BI35.** WHEN a `billing.invoice.issue` request names an order whose active hold has amount zero, THE SYSTEM SHALL issue an invoice whose `totalAmount` is zero, append one `consume` entry of amount zero and emit one `invoice.issued.v1`.

> *New in #9, owed by feature 19's gate ruling G1* (`progress/spec_billing_credit.md` § Gate ruling: *"a zero-total order … is consumed at invoice issue … and the saga completes"*; `BC38`). **B6** allows `totalAmount = 0`; **O3** allows a zero-total order. #7 and #8 both refuse it at this step (`activeHold <= 0`), so neither completes such an order.

**BI36.** THE SYSTEM SHALL render every amount named in the message of an invoice domain error with the shared ISO 4217 money-text formatter, never as raw minor units, while the error's machine-readable attributes stay integer minor units.

> *New in #9 as an id; #8 id 102's lesson, feature 19's `BC39`, extended to the five invoice errors that name an amount (`design.md` §5.6).*

**BI37.** WHEN a `billing.invoice.list` request asks for a page whose offset `(page − 1) × pageSize` exceeds 9 223 372 036 854 775 807, or an `issuedBeforeMinutes` whose cutoff precedes the earliest representable instant, THE SYSTEM SHALL answer success with no items and the true `page.total` — a page past the end, not an error; and THE SYSTEM SHALL answer `billing.credit.list` and `fulfillment.stock.list` the same way for an out-of-range offset.

> *New in #9, gate point **G1** (`design.md` §16.1).* Measured for this spec: an offset of `2⁶³ − 1` returns `[]`; `2⁶³` raises `DBAPIError` (`invalid input for query argument $2 … value out of int64 range`, SQLSTATE `22000`), which the responders answer `INTERNAL_ERROR`; `now − timedelta(minutes=2_000_000_000)` raises `OverflowError: date value out of range`. Both requests are schema-valid (`PageRequest.page` and `issuedBeforeMinutes` have a minimum and no maximum). #7 (JavaScript numbers) and #8 (`int` paging, unchecked) did not decide it.

**BI38.** THE SYSTEM SHALL prove the discount end to end with fixtures in which `amount`, `discount` and `totalAmount` are three pairwise-distinct, non-zero values, none of which contains another, the gross derived from the lines; and a mutation that drops, zeroes or ignores the discount at the wire decode, at the domain's total, at the `invoices.discount` column or at the fact's `discount` field SHALL fail a named test.

> *New in #9 as an id; it is this feature's third acceptance item and #8's round-1 blocking defect `D2`* (`../order-to-cash-dotnet/progress/review_billing_invoicing.md` D2: replacing the request's discount with `0` at the responder left **199** unit and **74** integration tests green, because every issue request the suite sent carried a zero discount, mapped to an absent key).
