## Decisions

* **Notifications needs neither `range_guards.py` nor `types.py`.** Asked and decided: its only table has no integer column and no payload column (live catalog: 5 columns, uuid, varchar(50), timestamptz(3)). A copy would guard nothing and add a file the census must police. `models.py` says so, and the parity census (`MEMBERS` = orders, fulfillment, billing) fails if one appears (arms X2, X3). It still takes all four dependencies: `alembic` and `sqlalchemy`/`asyncpg` for the migration, `pydantic-settings` for the URL.
* **Money columns: 7 in billing, 13 in total.** Command: `sed -n 241,305p "Order To Cash - Databases.EN.md" | grep -n -i cents` prints 5 lines (line 39 names `amount`, `discount`, `total_amount`), so 5 spec lines carry 7 columns: `credits.credit_limit`, `credit_items.amount`, `invoices.amount/discount/total_amount`, `invoice_items.price`, `payments.amount`. Orders: `sed -n 41,193p ... | grep -c -i cents` = 6 (feature 9). Fulfillment: 0 (feature 10). 6 + 7 + 0 = **13 = #8 id 44's "all 13 money columns"**. #8's "13" was a count of columns across the three databases, not of billing's lines.
* **Integer classification of billing's 11 integer columns** (read live, closed literal in `test_billing_quantity_range.py`): 1 quantity (`invoice_items.units`, code `quantity.out_of_range`), 7 money (`bigint`, generic `storage.integer_out_of_range`; `Money` is bounded to int64 in the domain and `specs/shared/` has no money-specific refusal code), 3 counters (`invoice_number_sequences.id/next_value`, `outbox.seq`, generic). The population test asserts the code per column, so a mis-classification fails (arm G2).
* **Counter table `invoice_number_sequences`** is single-row (`id = 1`), as fulfillment's. `id` is `integer`, not #7's `tinyint`.
* **Template mitigation (the 90 s threshold was crossed).** Root `conftest.py` builds one migrated template per service per session (by that service's own Alembic history, in a worker thread, engine disposed, no open connection) and hands each test `CREATE DATABASE ... TEMPLATE` of it, dropped at test end. Tests that exercise the migration itself keep `fresh_database` + `alembic_runner` (an empty database). This forced a four-line edit of `migrated_db` in orders' and fulfillment's `conftest.py` (outside "no changes to orders or fulfillment beyond 208(a)", but the brief names the mitigation and it cannot work without it); no test body changed.
* **Parity test places and loops:** `tests/database_parity/`, four databases migrated once per module by a sync fixture (each `asyncio.run`/Alembic run owns its loop), arms work on `CREATE DATABASE ... TEMPLATE` copies so the four references stay untouched. The three arms the brief lists are permanent tests, not one-off mutations (plus two more).
* **Parity shape** reads, per table: every column (information_schema joined to `pg_attribute`: `format_type`, nullability, identity kind, all identity sequence parameters, default, generated, collation, length, precision), every index (whole `pg_indexes.indexdef` plus `pg_index`: unique, primary, nulls-not-distinct, `indoption`, `indnkeyatts`, access method, ordered columns), every constraint (`pg_constraint`). Never SQLAlchemy metadata.
* **Settings:** copied from fulfillment, with 208(b): the fixture clears all six alias variables and a test asserts that the cleared set equals the set the class declares, so a new alias cannot be forgotten.
