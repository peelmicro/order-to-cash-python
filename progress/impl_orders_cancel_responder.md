## 1. What was built, per starting status

`orders.cancel` is answered by the Orders service on the same responder task and queue group as `orders.create` and `catalog.reference.list` (a third `ROUTES` entry). `CancelOrderCommand` is handled by `CancelOrderCommandHandler`, which loads the order with `get_by_id_for_update` (SO17), inside one unit of work.

| Starting status | Reply (`OrdersCancelReplyPayload`) | Commands issued, in order | Facts | End state |
|---|---|---|---|---|
| `placed` | `status: cancelled`, `cancellationReason: operator_cancelled`, `compensationPlanned: []` | none | `order.cancelled.v1` (note, no steps) in the same transaction | `cancelled` |
| `stock_reserved` | `status: stock_reserved`, `compensationPlanned: [stock_release]` | `stock.release` (reason `order_cancelled`) | `stock.released.v1` then `order.cancelled.v1` (note; one step built from the observed fact) | `cancelled`, `operator_cancelled` |

## 2. The six questions

**1. Where "an accepted operator cancellation" lives.** In `saga_commands`, as the order's `stock.release` row whose request carries `reason = order_cancelled` (`SqlAlchemySagaCommandQueue.find_accepted_operator_cancel`, `command_queue.py`): `order_id` AND `command = 'stock.release'` AND `json_extract_path_text(payload, 'reason') = 'order_cancelled'`; no status filter (a `sent`, `parked` or `rejected` row still means it was requested). #7 reads a triggering-envelope `eventType` (`../order-to-cash-nestjs/apps/orders/src/infrastructure/saga/drizzle-saga-command-store.ts:95`, `operator-cancel-envelope.ts:9-30`), #8 the same by content (`../order-to-cash-dotnet/src/Orders/Infrastructure/Saga/EfCoreSagaCommandStore.cs:342-353, 374-387`). #9's table has no envelope column (feature 27 owns `triggering_event_envelope`, `triggering_event_topic`, `dead_lettered_at`: `specs/order_saga_orchestrator/design.md` 9.8 item 2), so the question is asked of what is already stored and what was SENT to Fulfillment: the request's own `reason`. Options weighed: (a) a boolean column on `saga_commands` - cheaper to query, but a second statement of a fact the request already makes, free to drift from it; (b) feature 27's envelope columns - not mine to create (design 9.8) and not needed; (c) the order row - would change the aggregate (`domain/` is out of bounds) for a saga detail. Trade-off accepted: the query reads inside a `json` column (never `jsonb`, CLAUDE.md), once per late approval and once per operator-reason cancel.

**2. Where the note lives.** `saga_commands.operator_note` (`text`, nullable), written by the cancel's enqueue of the `stock.release` row and read back by the same query when the fact that completes the cancellation arrives. **A migration was needed** (`0002_saga_commands_operator_note.py`, additive, one nullable column): no existing column can hold free text from a request - `payload` is the verbatim `stock.release` request, which declares no `note` (`asyncapi.yaml` `StockReleaseRequestPayload`), `triggering_event_id` is a uuid, `last_error` is the dispatcher's. It is not one of feature 27's three columns, so 27's migration (revision `0003`) is independent. Checked: `tests/database_parity/` only compares `outbox` and `processed_events` (unchanged); the three Orders guards whose literals changed are in section 5. The note never reaches a wire payload the contract does not declare: `test_the_note_posted_reaches_the_row_that_will_complete_the_cancellation` asserts `"$where" not in payload`, and `test_a_compensating_status_enqueues_the_operators_stock_release_signals_it_after_commit_and_changes_nothing_else` asserts the exact request text `{"orderReference":"ORD-000007","reason":"order_cancelled"}`.

**3. Replies and errors.** See the table in section 1. HTTP through the Gateway (`rpc_error_classification.py`): `ORDER_NOT_CANCELLABLE` 409, `NOT_FOUND` 404, `VALIDATION_FAILED` 400 (the Gateway's backlog 215 owns that undeclared status), 503 only when nobody answers. `orderId` is REQUIRED by the responder although the schema lists only `reason` (#7 `orders-cancel.dto.ts`, #8 `OrdersCancelRequestValidator.cs`: the Gateway always sends it); a request naming only `orderReference` is refused `VALIDATION_FAILED`.

**4. The race against forward progress.** The cancel takes the SAME lock as a saga step, in the same place: `get_by_id_for_update` (SO17) as the first statement of its transaction. #7 read outside the transaction (`cancel-order.handler.ts`, the F1 race it live-reproduced); #8 took `UPDLOCK` (`EfCoreOrderRepository.cs:61-108`). Two outcomes, each constructed with a held lock (a third connection holds `FOR UPDATE`; each writer is observed WAITING in `pg_stat_activity`; the lock is then released; PostgreSQL queues waiters in arrival order): **cancel first** - the saga's `credit.approved.v1` finds the accepted cancel, owes `credit.release` and changes nothing (`test_outcome_one_...`); **saga step first** - the order is `confirmed` when the cancel gets the lock, the reply plans stock then credit, a `despatch.create` row already exists, the `stock.release` row carries the note (`test_outcome_two_...`). Armed: H1b (lock removed from the cancel), H11 (from the saga step).

**5. SA-4's despatch race.** Release wins: `stock.released.v1` at `credit_approved`/`confirmed` owes `credit.release` (status unchanged); `credit.released.v1` then cancels (`operator_cancelled`, steps stock then credit) - `test_sa4_from_credit_approved_and_confirmed_...`. Despatch wins: no `stock.released.v1`, no `credit.release`, `order.despatched.v1` moves the order on, no `order.cancelled.v1` - `test_the_despatch_wins_...[already_released | precondition_failed]`. **A `PRECONDITION_FAILED` on a lost `despatch.create` is terminal in #9's dispatcher today** (`nats_saga_commands.py:65-70`, `TERMINAL_RPC_ERROR_CODES` includes it): the row is `rejected` after one attempt, no retry, no park, no `order.saga_failed.v1` - proved by `test_a_despatch_create_refused_precondition_failed_after_the_release_won_...`. **Live finding (section 9):** the REAL Fulfillment answers the operator's `stock.release` with `PRECONDITION_FAILED` ("a reservation that is 'consumed' cannot become 'released'") when the despatch won, not `already_released`; Orders resolves that row to `rejected` (terminal) and the end state is the spec's (nothing released, no fact, no credit release). `saga.md` 4.3 does not say which reply, so no spec change is implied; the test covers both replies.

**6. The late `credit.approved.v1`.** Checked before the generic dispatch (`fact_handler.py`): the order is `cancelled` with `operator_cancelled` (read from the aggregate) OR still `stock_reserved` with an accepted cancellation (question 1's query). Then `credit.release` is enqueued and NOTHING else (no save, no `order.confirmed.v1`, no `despatch.create`). Kept out: `cancelled` with `credit_rejected` or `stock_rejected` (ignored, `precondition_unmet`); `stock_reserved` whose only `stock.release` row is the saga's own (`credit_rejected`): the query says no and the ordinary path decides; every other status. Armed: deleting the branch (F1, F1b, F1c), inverting each precondition (F2, F3), always-true (F4), enqueueing the wrong command (F7), falling through (F8).
