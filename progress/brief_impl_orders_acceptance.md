## Questions you must answer in the code and the report (research; nothing here is pre-decided)

1. **Transport errors (#8 D1, the blocking one).** How does nats-py signal *no responders* versus *timeout* on a request? Establish it by running it against a real NATS server, not from the docs (#8 found its library contradicting its own documentation). Each maps to a different `RpcError.code`; feature 42 depends on the split. A test must fail when the two branches are collapsed.
2. **`success | RpcError` decoding (#8 id 46, plan).** How is an error-shaped stock-check reply told apart from a success reply before typed decoding, and what does a malformed (non-JSON) reply become? Never a bare exception out of the handler.
3. **Request validation (#8 D5).** Which fields does `asyncapi.yaml` mark required on `orders.create`'s request? Every one has a test that fails when its check is deleted, and deleting the validator's **call site** fails a test too (#8 round 3: design the test so that an unvalidated request yields a *different* code, not accidentally the right one).
4. **Composition root (items 4, 6, 7, 8).** How does the lifespan prove the wiring at boot — a missing binding, a command with zero or two handlers — and does the guard drive the *real* `create_app()` / lifespan path rather than supplying the configuration itself (#8 D6: the test proved the container validates when asked, not that the host asks)? How is every env read reachable from the composition root guarded (#8 id 56)? 5. **Allocator (#8 A11, owed by #8 and never paid).** Prove `FOR UPDATE` allocation directly: N concurrent allocations in N real transactions yield a gap-free, duplicate-free set; a rolled-back order burns no number; seeding over a non-empty `orders` continues above the max. Arm the lock.
